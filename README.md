# Perfume Store AI Assistant

The approved customer chat and admin components now use Next.js server routes. No Express server is needed. Normal operation never calls the fixture answer service or plays assistant-sample.wav.

## Local setup

Use Node.js 22.13 or newer (tested on 22.23.2). Data is stored in Postgres (Neon) via DATABASE_URL; tests use in-process PGlite and never touch it.

From PowerShell:

```powershell
Set-Location 'D:\ahmed webs\projects\perfume-ai-assistant\frontend'
npm ci
Copy-Item .env.example .env.local
npm run owner:hash
```

Edit .env.local locally. Set DATABASE_URL, set OWNER_USERNAME and copy the generated salt:hash into OWNER_PASSWORD_HASH. The password prompt hides input; no plaintext password is stored. Populate GEMINI_API_KEY and GROQ_API_KEY locally. Do not paste keys into chat or use NEXT_PUBLIC variables.

Keep APP_ORIGIN exactly equal to your browser origin, including port, without a trailing slash. The default is http://localhost:3000. Configure HTTPS for any non-loopback environment. Admin and customer cookies are HttpOnly and SameSite=Strict; Secure is required on HTTPS and disabled only for local HTTP loopback.

```powershell
npm run dev
```

Open http://localhost:3000/owner to sign in as the owner and create usernames and passwords. Each person signs in with their assigned account to chat at http://localhost:3000 and to use http://localhost:3000/admin; one sign-in covers both, and their conversation history is saved to the account. The assistant refuses requests without a signed-in account before any provider is called, so no credits are spent. A direct admin URL always performs server authorization and redirects unauthenticated users to /login.

For a local production run:

```powershell
npm run build
npm start
```

With keys and free-tier confirmation configured:

```powershell
npm run providers:check -- 'D:\path\to\your-real-urdu-recording.webm'
```

The recording must be an actual Urdu speech recording of up to 60 seconds, under 5 MB. The script checks model availability, asks a catalogue/payment question, transcribes the recording, and attempts the exact requested Urdu TTS sentence. No recording argument means transcription is explicitly reported as unrun. Read and compare the transcript yourself.

Results are saved under the Git-ignored provider-check-output directory:

- answer.json — real generated text answer.
- transcript.txt — real supplied-recording transcription, if provided.
- urdu-review.wav — real generated TTS sample, only if the provider succeeds.

Play urdu-review.wav locally and assess Urdu pronunciation, PKR 2,500, mixed English words, voice consistency and whether the spoken words match the requested text. Only then set URDU_TTS_APPROVED=true. If unsupported or unusable, keep it false and report the limitation before choosing a substitute. While false, voice queries still return real transcription and answer text with audioStatus=unavailable.

To audition the currently configured voice independently of transcription, run `npm run speech:sample`. It writes `provider-check-output/pakistani-urdu-review.wav`. To create a synthetic Pakistani male Urdu voice, run `npm run speech:sample -- --design-pakistani` after confirming free-tier access. Voice design uses Gemini 3.8 Flash TTS; ordinary playback stays on the configured Flash-Lite TTS model. Only after successful synthesis does the script update `GEMINI_TTS_VOICE` in `.env.local`. Review the accent by listening, then restart the server if environment changes are not loaded. Designed voices are project-specific and expire after one year according to [Google's voice design documentation](https://ai.google.dev/gemini-api/docs/voice-design). Keep the voice ID in local configuration. `GEMINI_TTS_STYLE` controls delivery; the designed voice controls the regional accent.

## Server behavior

POST /api/chat accepts query (1–2,000 characters), requestId (UUID), and optional conversationId. It returns the existing structured service response plus conversationId. It does not generate audio for text queries.

POST /api/voice-query accepts multipart fields audio, audioDurationSeconds, requestId and optional conversationId. Browser MediaRecorder WebM/Opus, MP4 and Ogg, plus WAV, are supported. The declared duration is validated but never trusted: ffprobe inspects the actual container, streams and packet timestamps, including WebM without a duration header. Recordings have a 5 MB / 60-second limit, are held only temporarily, and are deleted in a finally block. Whisper uses transcription with automatic language detection, never the translation endpoint.

Both routes call the same Gemini answer service. Every turn loads the latest stored catalogue and policies. The prompt treats customer messages as untrusted, asks for clarification when ambiguous and forbids unstored claims. Recommendations are built from the real catalogue after validating the model's ID. Unsupported numeric claims and malformed structured answers are rejected. Generative language still needs real-provider acceptance testing; numeric checks cannot establish the truth of every prose claim.

History comes from successful server-stored turns, not customer-supplied conversationHistory. Conversation IDs are bound to an opaque customer session. Up to 12 previous turns are sent to Gemini. New conversation starts a fresh context. Conversations persist for review through authenticated GET /api/admin/conversations (optional ?id=...); the current chat UI does not restore history after a browser reload.

Duplicate request IDs replay completed responses. Concurrent turns in a conversation are rejected. The client retains request IDs for uncertain network outcomes, and explicit retries after a confirmed failure make a new attempt. No automatic provider retries occur.

Successful voice responses return the customer's transcript separately from the assistant text, private audioUrl, audioDuration and audioStatus=ready. On TTS failure, successful transcription and answer text still return with audioStatus=unavailable. The customer transcript appears on the customer bubble; the assistant bubble accompanies its own answer. AudioPlayerContext retains a single active player shared by chat audio and recording previews. Generated speech receives exactly the approved answer text and one configured voice.

GET /api/audio/:id requires the owning customer session and supports byte ranges for playback/seeking. Generated WAV data expires after 15 minutes; deletion runs each minute while the process is running, on requests and on the next startup. Expired audio is never accessible. Original uploads are not persisted. Browser recording object URLs are revoked on new conversation/unmount; audio files never go in public storage.

## Persistence and administration

The database seeds the existing fictional catalogue and policies once, including Velvet Oud at PKR 2,500. Seed bank/payment details remain fictional demo information. Enquiries start empty; fabricated sample enquiries are not seeded.

The admin UI saves through authenticated GET/PUT /api/admin/store. Product create/edit/delete preserves the approved component controls. Policy edits affect the next answer. Enquiry status/notes updates preserve server-owned enquiry content. A revision check prevents two admin sessions from silently overwriting each other's saved edits.

Credentials use salted scrypt; sessions are random opaque tokens stored only as SHA-256 hashes with expiry. Every admin API checks the admin role independently. Mutations require a matching Origin. Logout revokes the server session. The demo supports one environment-configured admin account, without registration, password recovery or role management.

Human handoff saves an enquiry for admin review. No email/SMS/WhatsApp notification or guaranteed callback is implemented, and the UI does not claim one was sent.

Reset requires ENABLE_DEMO_RESET=true, a signed-in admin, matching Origin, and confirmation=RESET DEMO DATA. The UI asks for confirmation. It restores products/policies and deletes conversations, audio and enquiries; it preserves admin sessions and rate-limit counters. Reset is rejected while a provider turn is active.

Conversations of signed-in accounts are kept; anonymous visitors' conversations/enquiries are removed after 30 days, cleaned on the same schedule as audio. Private audio is stored in the database with its 15-minute expiry. Database writes inside transactions serialise on a Postgres advisory lock. Nothing has been deployed.

## Limits and errors

Public limits are 10 text requests, 4 voice requests and 5 login attempts per minute per trusted IP; with TRUST_PROXY=false, all callers share a conservative local bucket. Global ceilings also apply. Provider attempts are capped locally at 8 Gemini / 10 Groq per minute and 100 per provider per day, including failed attempts. These are conservative app ceilings, not assertions about your account quota. Whisper's worst-case daily audio use is therefore 6,000 seconds at the app's maximum recording length.

Request bodies are bounded even without Content-Length. Upload reads have a 15-second limit, transcription/text provider calls 35 seconds, TTS 45 seconds and audio probing 8 seconds. Quota failures return 429; invalid input 400/413/415/422; unavailable providers 503; conflicting requests 409. Responses use private, no-store headers. Provider error details and credentials are not returned or logged. Failed transcription asks the customer to retry or type.

## Human-readable API responses

Every JSON success response includes `success: true` and a readable `message`, alongside its existing object fields. Conversation list/message arrays are returned in `data` alongside those fields. Voice responses also include `audioUnavailableReason` when transcription/answer succeeds but speech generation fails or awaits Urdu approval.

Errors include `success: false`, `message`, the existing `error` alias, and a machine-readable `code`. Invalid fields include a `details` list with field names and validation messages. Credentials, submitted secret values, provider internals and stack traces are not included.

Unsupported methods return 405 with a readable explanation and an `Allow` header. Successful audio stays binary WAV and provides its explanation through `X-Response-Message`; invalid byte ranges return a JSON error with 416 and `Content-Range`. Error `X-Response-Message` headers are URI-encoded for safe transport.

Example invalid chat input:

```json
{
  "success": false,
  "message": "Some fields are missing or invalid. Check the field details and try again.",
  "error": "Some fields are missing or invalid. Check the field details and try again.",
  "code": "invalid_input",
  "details": [{ "field": "query", "message": "Too small: expected string to have >=1 characters" }]
}
```
